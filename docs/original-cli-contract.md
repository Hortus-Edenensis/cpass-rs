# 原版 CLI / TUI 契约整理

本文档用于从原版 Python 入口还原“用户直接执行程序时，程序应当表现成什么样”，
避免继续把当前 Rust CLI 的某个局部行为误当成原版契约。

## 证据来源

本次整理基于以下原版备份与入口文件：

- 备份归档：`/tmp/cpass-rs-worktree-46d3-before-rs-20260412142011.tar.gz`
- 原版入口：`main.py`
- 原版交互：`dialog.py`
- 原版说明：`README.md`
- 原版配置：`config.yml`

这些文件都来自同步 Rust 工作树之前的旧 worktree 备份，因此比当前 Rust CLI 的实现更能代表
“原版直接运行程序”的交互契约。

## 原版启动契约

### 1. 直接执行主程序就进入交互模式

原版不是“必须带子命令”的 CLI。

用户运行：

```bash
python3 main.py
```

程序会直接进入交互式终端应用，而不是先要求用户输入 `run --tui` 这一类命令。

这意味着**顶层入口本身就是一个交互式应用启动器**，而不是一个纯命令式 dispatcher。

### 2. 启动后先展示 logo / banner

原版入口第一步会调用 `dialog.logo(console)`。

因此用户启动程序后，首先看到的是品牌 banner / 版本信息，而不是直接跳进课程执行视图。

### 3. 启动阶段先做“会话管理”，不是先做课程执行

原版入口启动后先读取本地会话存档：

- 如果存在会话：
  - `multi_session: true` 时进入“会话选择”界面
  - `multi_session: false` 时自动加载第一个会话
- 如果会话失效，会尝试自动重登
- 如果没有会话，则提示用户登录

因此顶层契约是：

> **先解决“我是谁 / 用哪个账号”**，再进入课程或考试交互。

这与“直接打开课程执行 TUI”明显不同。

### 4. 原版登录是启动流的一部分

原版 `dialog.login()` 支持两条交互路径：

- 手机号 + 密码登录
- 留空手机号后进入二维码登录

也就是说，原版“直接运行程序”时，登录是被内嵌在启动流程中的，而不是要求用户先单独执行
`cpass login` 再回来。

### 5. 登录 / 会话解决后，会显示账号信息

原版在启动主流程前会打印当前账号信息，并记录日志。

因此原版顶层入口在语义上不只是“选课工具”，而是一个：

1. 账号入口
2. 会话入口
3. 课程 / 考试入口
4. 任务执行入口

串起来的完整交互应用。

### 6. 顶层交互的下一层是“课程 / 考试选择器”

原版在获取课程列表后调用 `dialog.select_class()`，这里的契约不是单纯输入一个课程 index。

它支持：

- 课程序号
- 课程名称
- `courseId`
- 输入 `q` 退出
- 在输入前加 `EXAM|` 前缀进入考试模式

所以原版的顶层选择器是**课程 / 考试路由器**，不是“课程 index 选择器”。

### 7. 考试模式还有二级交互

如果课程选择阶段进入考试模式，原版还会进入 `dialog.select_exam()`：

- 先展示考试列表
- 用户输入序号选择考试
- 输入 `e<序号>` 进入导出模式
- 输入 `q` 退出

这说明原版契约包含：

- 一级：会话 / 登录
- 二级：课程 / 考试模式选择
- 三级：考试选择 / 导出选择

### 8. 任务执行 TUI 是“后置视图”，不是顶层首页

原版 `main.py` 中的任务执行分为：

- `fuck_task_worker(...)`：章节任务点执行 TUI
- `fuck_exam_worker(...)`：考试执行交互

其中章节任务点 TUI 使用 `rich.layout + rich.live` 做分屏和实时刷新。

这说明原版的 TUI 契约是：

> **任务执行 TUI 是进入具体课程/考试后的工作视图，不是程序启动首页。**

### 9. 顶层程序还负责统一退出语义

原版启动流内建这些退出行为：

- 会话选择阶段输入 `q`
- 课程选择阶段输入 `q`
- 考试选择阶段输入 `q`
- `KeyboardInterrupt`
- 正常任务完成后打印“任务已完成, 程序退出”
- 运行异常时打印错误说明和日志提示

也就是说，原版顶层入口不仅负责启动，还负责统一的退出 / 错误提示语义。

## 从原版提炼出的“顶层契约”

如果只看“直接运行程序”的用户体验，原版可以归纳为：

1. 直接执行程序即可进入交互应用
2. 先展示 logo
3. 先解决会话 / 登录
4. 再展示账号信息
5. 再进入课程 / 考试选择
6. 再进入具体任务执行 TUI
7. 顶层入口统一处理退出、异常、完成提示

换句话说，**原版的顶层入口是一个完整的交互式编排器（interactive orchestrator）**，
不是“直接跳转到某个具体执行视图”。

## 与当前 Rust 实现的关键差异

当前 Rust CLI 主要是“显式子命令”模型：

- `doctor`
- `config validate`
- `login`
- `courses list`
- `tasks scan`
- `exam ...`
- `run`
- `run --tui`

这套模型本身没有问题，但它和原版的**顶层入口契约**不是一回事。

特别是，之前把：

> “直接执行 `cpass` 时先列出课程，再立即进入 `run --tui`”

当成“原版契约”

这是**不准确的**，因为它跳过了原版真正存在的：

- logo
- 会话管理器
- 账号重登逻辑
- 二维码 / 密码登录分流
- 课程 / 考试模式路由
- 课程名 / courseId / index 混合选择
- 考试二级选择

所以，如果要“对齐原版”，目标不应该是：

> 让 `cpass` 直接进入当前的 run-TUI

而应该是：

> 在 Rust 里补一个与原版等价的**顶层交互入口**，把会话、登录、课程/考试选择和执行视图串起来。

## 后续实现约束

后续若要继续对齐原版，应至少满足下面这些约束：

### 顶层入口

- 直接执行 `cpass` 可进入交互模式
- 不是直接跳进任务执行视图

### 会话 / 登录层

- 需要先解析当前 saved session
- 多会话时提供交互式选择
- 没有会话时能在顶层入口里触发登录
- 账号失效时能在顶层入口里引导重登

### 课程 / 考试路由层

- 至少要有课程选择器
- 不能把“只支持 course index”误当成原版等价物
- 需要单独考虑原版的 `EXAM|` 模式路由

### 执行层

- 当前 `run --tui` 可以作为“章节任务执行视图”的底座
- 但它只是整个原版交互应用中的一个后置执行视图，不应单独冒充完整首页

## 当前结论

原版契约已经明确：

> **直接执行程序 ≠ 直接进入当前 Rust 的 `run --tui` 页面**

原版真正的契约是：

> **直接执行程序 → 会话/登录 → 课程/考试选择 → 具体执行 TUI**

后续 Rust 侧应先按这个契约拆出“顶层交互编排器”，再讨论如何复用当前
`run --tui`、`login`、`courses list`、`exam ...` 这些底层能力。
